## Product and delivery boundary

Deliver a commercial shipment workspace that reuses company, customer and product data to produce consistent document sets and repeatable shipment history. This is the complete production product, not a reduced MVP. Personas include small importers/exporters, manufacturers, wholesalers, freight teams, trade consultants preparing drafts, and internal support/compliance operators.

TradeDocs is not a customs broker, carrier, chamber, issuing authority, legal adviser, sanctions service, tariff classifier or provider of negotiable transport documents without a separately authorized and validated workflow. Generated material must never imply official issuance, endorsement, customs clearance, origin proof, transport title or legal compliance. Finalized documents must remain immutable, reproducible and traceable to shipment revisions. Unknown regulatory behavior must remain disabled with an explicit limitation.

Required stack: Next.js App Router and strict TypeScript; accessible responsive components; Supabase Postgres/Auth/private Storage with migrations, generated types and RLS; provider-neutral Payment Links with verified webhooks and entitlements; Vercel preview/staging/production; Resend and React Email; server-side versioned PDF rendering; GA4/Search Console/IndexNow; Sentry/Turnstile/distributed rate limits/structured logs/health checks; GitHub CI/CD and tested recovery.

Required inventory: profiles, organizations, memberships, companies, contacts, parties, addresses, products, product_variants, shipments, shipment_items, packages, package_items, transport_legs, document_sets, documents, document_revisions, templates, attachments, render_jobs, numbering_sequences, orders, payments, entitlements, email_events, audit_events, regulatory_sources and feature_flags.

## Gates shared by every task

Every task must map acceptance criteria to implementation and evidence, run format/lint/strict typecheck/unit/affected integration/production build checks with zero unexplained warnings, cover relevant Playwright happy path/validation/authorization/retry or reload/mobile behavior, check affected accessibility and prove isolation for each new tenant data path. PDF and visual work requires rendered inspection and regression fixtures. A non-applicable check needs an explicit scope rationale; missing, skipped or failed required checks are not success.

Read the master instructions, dependencies and affected living documents before edits. Inspect and preserve existing user work. Implement the smallest complete production slice, inspect actual UI/output, update documentation and CHANGELOG, then make one focused conventional commit per task. Record approved deviations with rationale and impact in DECISIONS.md. Each task report must link its commit, test output, screenshots/rendered samples, migrations and rollback notes, updated documents and remaining risks. Tests may not be weakened by relaxing auth, RLS, validation, audit, webhook or privacy controls. Flaky tests require an owner and expiry if quarantined.

Maintain PRODUCT.md, ROADMAP.md, ARCHITECTURE.md, DATABASE.md, SECURITY.md, LEGAL.md, SEO.md, ANALYTICS.md, DESIGN_SYSTEM.md, OPERATIONS.md, TEST_PLAN.md, RUNBOOK.md, CHANGELOG.md, AGENTS.md and ADRs, with ownership and review triggers. Every exposed database table/view/function needs an explicit access decision and RLS evidence. Authenticated callbacks/jobs must be idempotent, observable, retry-safe and replay-resistant; UI actions need loading, success, empty and recoverable error states. Never put sensitive document data into analytics/logs/error breadcrumbs or expose privileged credentials.

## Dependency analysis and safe parallel work

The PDF permits reordering only when a dependency graph proves safe parallelism. On its literal graph, 01→02→03→04→05 precedes two independent branches: billing/email/analytics/SEO/CI (06→07 and 06→08→09→10) and the trade data chain (11→12→13). Once 06 passes, 07 and 08 can proceed independently; after schema/legal prerequisites, 15, 16 and 17 can be implemented by separate owners with shared schema interfaces. Integration/release acceptance still waits for every dependency and required gate.

The literal graph contains an unresolved cycle: **14→24→14**, also **17→24→17**, and **22→24→23→22** (arrows mean “depends on”). It therefore cannot be used as a complete topological delivery order. Proposed resolution for recorded approval: establish an initial 24A registry schema/source inventory/approved copy checkpoint before 14–17 and 22; keep the complete Task 24 admin, monitoring, review-evidence and rollout acceptance after 23/10. This is a proposal, not an approved scope reduction or completed Task 24. Engineering can inventory sources and design the registry before approval; affected legal claims stay disabled.

Task 10 also requests a production generation smoke before Tasks 14–18 implement generation. Implementing its CI harness early is reasonable; its generation evidence must wait for real document workflows. Task 11's coherent-set criterion similarly needs later Task 19 integration evidence. Early data-model tests cannot substitute for these acceptance demonstrations. The task-order/evidence timing interpretation requires a recorded decision before claiming these tasks complete.

## Cross-cutting non-functional acceptance and final release gate

- Availability: 99.9% monthly authenticated/purchase flow target excluding scheduled maintenance; service SLOs and error budgets. Publish server action/API p50 and p95 latency.
- Performance: public p75 LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1. Compatibility: current and prior major Chrome/Safari/Firefox/Edge, 360 px mobile through large desktop and print-safe templates.
- Accessibility: WCAG 2.2 AA target, semantic headings, labeled controls, keyboard/focus/contrast/reduced motion and accessible document alternatives where feasible.
- Privacy/recovery: minimization, purpose limitation, retention, export/delete, consent-aware analytics, redacted logs and subprocessors; daily backups, tested point-in-time recovery where plan permits, quarterly restores, per-service RPO/RTO and versioned storage retention.
- Release requires all 25 task acceptance records, approved pricing/refunds/entitlements/support, no public placeholders/dead routes/fake testimonials/unfinished states, clean build/safe migrations/no critical dependency findings, all relevant unit/integration/E2E/a11y/PDF/load evidence and proven flags/rollback/compatibility.
- Security release evidence must cover threat model/RLS/no tenant leakage; secrets/logs/uploads/signed links/admin/retention/export/delete; working Turnstile and rate limits that preserve recovery. Commercial evidence must prove verified payment entitlement, refund/dispute reconciliation, receipts/mail, server revenue reconciliation and support resolution without DB editing.
- Operations must have live Sentry releases/alerts/health/dashboards/on-call/runbooks, completed restore with approved RPO/RTO/incident process, production synthetic/post-deploy smoke, valid canonical/robots/sitemap/schema, configured Search Console/IndexNow and approved primary-source claims with scheduled editorial/regulatory owners. A named human approves production credentials, legal/regulatory conclusions and go-live.

Post-launch loop: daily uptime/errors/queues/payment reconciliation/delivery/abuse/support; weekly acquisition/conversion/search/failures/repeat use/document adoption; monthly sources/access/backups/dependency risk/content decay/KPI prioritization; quarterly restore/tabletop/threat model/accessibility/vendor reviews. Prioritize security, billing integrity, data loss and regulatory correctness before experiments. Experiments need a declared metric, guardrail and stopping rule. New years/jurisdictions/document types/providers require versioned registry/schema/fixtures; preserve purchased historical artifacts and synchronize CHANGELOG/registry/runbooks/review dates.
